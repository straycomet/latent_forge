# Open WebUI — Setup, Use, and Lab Notes

Open WebUI is the browser-based interface used in this lab to interact with local model servers. It is not an inference engine itself; it sits above backends such as Ollama, llama.cpp, and other OpenAI-compatible APIs.

This repository treats Open WebUI as the **user-facing access layer** in the local AI stack.

## Where it fits

```text
Browser
   |
   v
Open WebUI
   |
   +--> Ollama
   |
   +--> llama.cpp OpenAI-compatible API
   |
   +--> vLLM OpenAI-compatible API
   |
   +--> custom tools / model profiles
```

That separation is useful because the UI can remain stable while the underlying model runtime changes.

## Lab status

**Implemented and in regular use.**

Open WebUI has been deployed in Docker and connected to local Ollama. It has also been used as the UI/orchestration layer around application-specific tools and custom model profiles.

The reusable infrastructure lesson is to keep Open WebUI's own state separate from application code and model runtimes.

## Basic Docker deployment

A simple deployment pattern is:

```bash
docker run -d \
  --name open-webui \
  --restart unless-stopped \
  -p 3000:8080 \
  -v open-webui:/app/backend/data \
  ghcr.io/open-webui/open-webui:main
```

Then open:

```text
http://localhost:3000
```

For a public repository, prefer pinning a tested image tag rather than relying indefinitely on `:main`.

## Connecting to Ollama

If Ollama runs on the same host outside Docker, Open WebUI must be given a host-reachable Ollama URL.

The lab has used:

```text
OLLAMA_BASE_URL=http://127.0.0.1:11434
USE_OLLAMA_DOCKER=false
```

Whether `127.0.0.1` works depends on the Docker networking mode. With normal bridge networking, container loopback is not the host. In that case use a host-reachable address or `host.docker.internal` where supported.

Verify Ollama independently first:

```bash
curl http://localhost:11434/api/tags
```

Then verify connectivity from inside Open WebUI:

```bash
docker exec open-webui \
  python -c 'import urllib.request; print(urllib.request.urlopen("http://<ollama-host>:11434/api/tags").status)'
```

Do not debug the UI and model runtime simultaneously. Prove the backend works first.

## Connecting to llama.cpp

llama.cpp can expose an OpenAI-compatible API. Start the server with the desired model and bind address, for example:

```bash
llama-server \
  -m /path/to/model.gguf \
  --host 0.0.0.0 \
  --port 8080
```

Then configure Open WebUI with the OpenAI-compatible endpoint:

```text
http://<llama-host>:8080/v1
```

Before adding it to Open WebUI, validate directly:

```bash
curl http://<llama-host>:8080/v1/models
```

and a minimal chat-completions request.

The important lesson from local agent testing is that "OpenAI-compatible" networking does not guarantee chat-template compatibility. A backend may be reachable while still rejecting the message-role sequence generated by a client.

## Connecting to vLLM

vLLM also exposes an OpenAI-compatible API.

A tested distributed vLLM deployment in this repository listens on:

```text
http://<vllm-head>:8000/v1
```

Verify it first:

```bash
curl http://<vllm-head>:8000/v1/models
```

Then add that base URL to Open WebUI as an OpenAI-compatible connection.

This lets Open WebUI sit above a multi-node inference service without needing to understand Ray, tensor parallelism, or pipeline parallelism.

## Persistent state

Open WebUI stores important state under:

```text
/app/backend/data
```

When containerized, keep that state in a named Docker volume:

```bash
-v open-webui:/app/backend/data
```

Do not destroy the volume during routine container replacement or upgrades.

Before migration or major upgrades, inspect the current mounts:

```bash
docker inspect open-webui \
  --format '{{range .Mounts}}{{println .Type .Name .Source "->" .Destination}}{{end}}'
```

A practical database backup is:

```bash
mkdir -p "$HOME/openwebui-backups"

docker cp open-webui:/app/backend/data/webui.db \
  "$HOME/openwebui-backups/webui-$(date +%Y%m%d-%H%M%S).db"
```

Backups should remain local/private unless sanitized; the database may contain user accounts, prompts, model configuration, and other private state.

## Application-specific tools

One implemented pattern was to mount only the minimum application resources needed by Open WebUI and keep them read-only.

The ChartSense deployment exposed only selected application code/config/data/tool definitions rather than mounting the whole host filesystem into the container.

That design principle generalizes well:

- mount only what the tool requires;
- use read-only mounts whenever write access is unnecessary;
- do not let application packages overwrite Open WebUI's own Python dependencies;
- provision tools explicitly rather than relying on accidental filesystem discovery;
- preserve access grants when updating tool definitions.

## Operational checks

Useful checks include:

```bash
docker ps --filter name=open-webui
```

```bash
curl -f http://localhost:3000
```

```bash
docker logs --tail 100 open-webui
```

```bash
docker inspect open-webui \
  --format '{{range .Config.Env}}{{println .}}{{end}}'
```

For Ollama-specific debugging:

```bash
docker inspect open-webui \
  --format '{{range .Config.Env}}{{println .}}{{end}}' |
  grep -E 'OLLAMA_BASE_URL|USE_OLLAMA'
```

## Strengths

### Backend independence

Open WebUI can sit above different inference runtimes, so the browser experience does not need to change when switching between Ollama, llama.cpp, or vLLM.

### Good local-AI ergonomics

It provides a familiar chat interface, model selection, conversation history, and administrative controls without requiring users to operate model servers directly.

### Useful orchestration surface

Custom tools and model profiles make it possible to turn the UI into more than a chat window while keeping the inference layer separate.

### Docker deployment is straightforward

Persistent state can be isolated in a named volume and the application can be replaced independently of its data.

## Trade-offs

### Another stateful service

Open WebUI introduces accounts, configuration, persistent history, tool definitions, and upgrades. Treat it as infrastructure, not as a disposable frontend.

### Networking can be confusing in Docker

`localhost` means different things on the host and inside a container. Many apparent model-runtime failures are really namespace/routing issues.

### Tool integrations increase security exposure

Giving Open WebUI tools access to files, databases, APIs, or application code broadens the trust boundary. Mount narrowly and avoid unnecessary write access.

### Image upgrades should be deliberate

A UI/database migration should not happen accidentally because a mutable container tag was pulled. Pin and test important deployments.

## Security guidance

For public or shared environments:

- do not expose Open WebUI directly to the public Internet without an appropriate authentication and network-control design;
- do not commit the Open WebUI database;
- do not commit API keys or provider credentials;
- use read-only application mounts where possible;
- back up persistent state before upgrades;
- treat custom tools as executable code with the privileges of the Open WebUI environment.

See [Security and Reliability](security-reliability.md) for the repository-wide policy.

## Recommended role in Latent Forge

Use Open WebUI as the human interface layer when you want one browser UI over multiple local inference engines.

Keep the responsibilities separate:

```text
Open WebUI     -> interface / orchestration
Ollama         -> convenient local model runtime
llama.cpp      -> flexible GGUF inference and experimentation
vLLM           -> higher-throughput / distributed serving
Hermes         -> autonomous agent runtime
```

That separation has made the local AI stack easier to evolve and troubleshoot.
